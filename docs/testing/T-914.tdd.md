## 1. User journeys

1. **An integration drops a folder on a share and asks "would this run?"** `POST /api/v1/jobs/validate` answers
   `200` or `422` with the reasons, takes no job id, writes nothing into the folder — not even `output/` — and
   never opens a QuickBooks session. Nothing is committed to by asking.
2. **A caller has to pick an account name the mapper will accept.** `GET /api/v1/quickbooks/lists` reads the
   cached `qb-lists.json`, so it answers while QuickBooks is shut down and never queues behind a post.
3. **The operator runs `deploy/start-all.ps1` at logon.** Before this task it waited on `/health/hermes`, which has
   needed `health:read` since session 15, and the script holds no key by design — so it would have logged "not
   healthy" for the full 180 s on every boot and exited 2 with the API perfectly fine. It now waits on
   `/api/v1/health/ready`, which needs nothing.
4. **The operator runs `scripts/qb-server-check.ps1 -Step health` on the QuickBooks server.** It called
   `/health/quickbooks` with no key and a comment saying none was needed: a 401, and the T-609 checklist stops at
   its first step. It now goes through `Invoke-Api`, which always sends the key.
5. **The owner reads the runbook to issue a key, turn the shared key off, find the audit file, or work out what a
   429 means.** All four are now in it (§3.4, §3.5, §3.6, §8.7); none of them were.

## 8. Decisions worth reading

1. **`POST /jobs/validate` answers `422` for an F1 error, while `POST /jobs` answers `400` for the same folder.**
   FR-A-7 names only `200`/`422`, and a validator that returns its body only on success is useless (FR-A-6's own
   rule). A *malformed* request — no `folder` at all — is still `400`, as is a folder outside
   `Paths:AllowedJobRoots`. The inconsistency with `POST /jobs` is deliberate and recorded as **Q-68**.
2. **The allow-list applies to the validate.** FR-A-7 does not mention it. Without it the route would answer
   "`requirement.txt` is missing" for any path on the server, which is a directory probe with a friendly name.
   Rule 4: the reading that reveals less.
3. **`POST /api/v1/quickbooks/lists/sync` was added beside `/qb/sync-lists`, not instead of it.** api-v1 §3 marks
   the route **R** (renamed), but §13's task list gave T-914 only the two new routes, and deleting a working path
   is not something to do unattended. Both are mapped, the document marks the old one `deprecated`, and **Q-69**
   asks when it goes. api-v1 §9.1 keeps the flat `/qb/sync-lists` alive regardless while `Api:LegacyRoutes` is true.
4. **A missing `qb-lists.json` is `200` with empty lists, not `404`.** `GET …/lists` is a cache read, and
   "nothing cached yet" is a true answer a caller can act on — `syncedUtc: null` says it. Readiness already treats
   the missing file as a **warning** (T-902), so this agrees with it rather than inventing a second opinion.
5. **`deploy/start-all.ps1` now waits on readiness, not on Hermes health.** It must hold no secret
   (`DeployScriptsTests` forbids the string `ApiKey` in it), and since session 15 `/health/hermes` needs a scope.
   Hermes is still proved — by `Wait-HermesPort` on 127.0.0.1:8642, before the API starts. A host that never
   becomes ready is now exit **1** ("the API could not be started"), which is what actually happened; exit 2 keeps
   its old meaning, "the API runs but Hermes is not up".
6. **G1 moved into `StatementCheck.Reconcile` rather than being copied.** FR-A-7 is only worth anything if its
   verdict is the job's verdict. Two copies of "which reconcile check applies" would eventually disagree, and the
   one that disagreed quietly would be the validate that told an operator a statement was fine.
7. **`Api:LegacyRoutes` stays `true`** (handoff §4). Moving the documentation is not switching the flat routes
   off, and nobody is here to confirm which callers still use them (Q-53).

## 9. Known gaps — what this does **not** prove

1. **Nothing here has run against a real QuickBooks or a real Hermes**, as with every task since T-907. Every
   QuickBooks answer in these tests comes from `FakeQbGateway`.
2. **The validate has never read a PDF statement.** Both sample statements are CSV, parsed by code. The PDF branch
   goes through `StatementReader` → `PdfText` → Hermes T2 exactly as a job does, and `TestStatementReader`'s
   default double *throws* if T2 is called, so these tests prove the CSV path never calls a model — they do not
   prove the PDF path works here, and they do not measure how long a folder of PDFs would hold the request.
   `PdfStatementApiTests` covers that path for a job, not for the validate.
3. **No test asserts the validate and a real job reach the same verdict end to end.** The shared
   `StatementCheck.Reconcile` makes the G1 step literally the same code, and the existing pipeline tests pass
   unchanged, but nothing runs both entrances over one folder and compares. `DirectAndFolderPathsAgreeTests` does
   that for the other pair of entrances; this one has no equivalent.
4. **`OperatorDocsTests` checks text, not truth.** It proves the documents name `/api/v1` routes and do not
   promise a key-free health check, and that seven subjects appear in the runbook. It cannot tell whether a
   sentence about them is *correct* — only a person reading it can, and that reading has not happened.
5. **Neither PowerShell script has been executed.** `qb-server-check.ps1` and `start-all.ps1` are checked by
   grepping their text (ASCII, no secrets, which route they call). Whether `Invoke-Api GET` actually works against
   a live host for `/api/v1/health/quickbooks` is part of the T-609 checklist, on the server.
6. **The POC package has not been rebuilt.** `samples/poc/appsettings.json` gained every M9 setting and
   `scripts/build-poc-package.ps1` copies it, but no `.zip` was produced or unpacked here, so nothing proves the
   packaged app starts with that file.
7. **`GET …/lists` has no cap.** A company with tens of thousands of names returns them all in one response. It is
   a local read of a file the app wrote, so nothing is unbounded that was not already on disk — but no test sends
   a large one, and no paging exists (**Q-70**).
8. **Rate limits are off in these tests** (`ApiFactory` pins `Api:RateLimits:Enabled` false, trap 14), so neither
   new route has ever met the limiter. The runbook now documents the 429 and its `Retry-After`; `RateLimitTests`
   proves the limiter works, on other routes.
