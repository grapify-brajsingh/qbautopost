# T-1603 server checklist: first install and releases on the Windows server

Tick each box on the QuickBooks server (and an accountant's PC where stated), in order. If a step does not match, stop,
write what you saw next to it, and do not go on. The agent checked the scripts and docs statically only: `deploy.ps1`, the
nginx contract and `appsettings.Production.json` have not been exercised on a real install. Background: `docs/runbook.md`
section 14 and `docs/windows-deploy.md`.

Run with a recent QuickBooks backup. Never write a password or key into this file.

- [ ] **1. The settings file is read.** After the first `deploy.ps1`, the API's startup log shows the values from
  `C:\qb-autopost\appsettings.Production.json` (company name and file, `BackupFolder`, `Paths:Clients`). Nothing has yet
  confirmed this file is read on a real install; if the log shows the defaults, stop.
- [ ] **2. Sign-in survives a reload.** From an accountant's PC, sign in over nginx's HTTPS address and reload the page:
  you are still signed in (the `Secure` refresh cookie works over nginx).
- [ ] **3. The audit shows the real address.** Open the audit feed after step 2: the sign-in shows the PC's address, not
  `127.0.0.1` (`Api:TrustForwardedHeaders` and `X-Forwarded-For $remote_addr` work).
- [ ] **4. A 10 MB PDF uploads and extracts.** Run `docs/testing/T-1215.server-checklist.md` through nginx
  (`client_max_body_size 11m`, `proxy_read_timeout 600s`).
- [ ] **5. A small post reaches QuickBooks.** The one trusted user posts a small statement; it appears in QuickBooks.
  If it fails on version, set `QuickBooks:QbXmlVersion` to `16.0` in `appsettings.Production.json`, restart, and record
  that in the tracker (Enterprise 24 may not take the default).
- [ ] **6. Deploy, lock and rollback.** (a) A second `deploy.ps1` with no changes completes and the dashboard answers.
  (b) Hold a file in the `app` folder open and run `deploy.ps1`: it fails and the old version is back and ready.
  (c) `deploy.ps1 -Rollback` restores the previous version. Note that `pre-deploy-*.dump` files stay in
  `<BackupFolder>\postgres` after each deploy.
- [ ] **7. The limited account can drive the task.** As the limited auto-logon account (not an administrator),
  `deploy.ps1` sees the scheduled task `QbAutopost` and starts it; the preflight does not refuse.
- [ ] **8. A task left Running is cleared.** `deploy.ps1` calls `Stop-ScheduledTask` only when task `QbAutopost` is still
  `Running` at start (`Start-Api`). Make that happen: for example start a version that never becomes ready, then run a
  restore or `deploy.ps1 -Rollback`. Expect: the task ends up not `Running` before it is started again, exactly one API
  process, port 5080 listening, and `/api/v1/health/ready` returns 200.
