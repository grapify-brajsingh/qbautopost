## 1. User journeys

1. As a calling system, I want to ask "would these rows post?" **before** the QuickBooks server is even running, so I
   can fix my data at my own pace instead of during a posting window.
2. As the owner, I want the answer to be the truth: a batch that validates clean must not turn into a post that holds
   half its lines.
3. As a caller whose batch is refused, I want the reasons — a validator that only explains itself on success is
   useless, so the 422 carries the same body as the 200.
4. As the owner, I want a duplicate caught here too, against the ledger, whichever entrance first posted it.
5. As the owner, I do not want the exact qbXML — every amount and name in the batch — handed to anyone who asks.

## 5. Decisions

- **The caller's account replaces the `rules.json` last-four lookup, per (kind, last4) group.** The folder path finds
  the bank account by last four; a direct caller names it. Rather than post-processing the mapper's output — which
  would lose the payee and tier resolution the mapper skips once it holds on `unknown-account` — the caller's account
  is injected into a scoped copy of the rules, so `Mapper` decides exactly as it would for a statement. One last four
  sent as two different accounts is a contradiction, so both rows hold `conflicting-last4`.
- **A control-total mismatch is 400, not 422.** §6.1 says `400 control-total-mismatch`; §2 reserves 400 for a request
  that is "self-inconsistent". `controlTotalOk` stays in the body (FR-A-6 lists it) and is therefore always `true`
  when a body is returned at all. Recorded because the two spec sections could be read as disagreeing.
- **A skip leaves the batch `ok`; a hold or a duplicate does not.** A skip pattern is a rule doing its job, not a
  problem awaiting a person.
- **`skipped` includes `duplicates`.** That makes `wouldPost + held + skipped = submitted`, so a caller can check the
  arithmetic of the answer as well as of the request — and it matches FR-A-6's own example (9 + 2 + 1 = 12).
- **An unknown name holds the row rather than only being reported.** QuickBooks would reject it at post time anyway
  (G5); a hold now is the same outcome, earlier and legible. Each list is consulted only when it has entries.
- **The qbXML body is withheld even when asked for.** FR-A-6 gates it on the `qb:debug` scope, which does not exist
  until T-910. Until a key can be *shown* to hold that scope, handing it to every holder of the shared key is the
  less careful of the two readings (CLAUDE.md rule 4). The response says so in `qbXml.note`.

## 6. Known gaps — what this does **not** prove

- **Tiers 3–4 never run here.** A row that Hermes would resolve is reported `no-account-rule`. The plan can therefore
  be *gloomier* than a post with `allowModelAccounts: true` — the safe direction, but it means "validate says held"
  is not proof that a post would hold. The reverse, which matters, is what tests 18–29 protect.
- **A clean validate is not a guaranteed post.** Three things can still change the answer: G4's QuickBooks half
  (`LiveDuplicateGate`, which needs the SDK), the FR-11 backup guard, and G5's echo check. With `qb-lists.json`
  unsynced, a name QuickBooks does not know also passes validation and is rejected at post time.
- **`allowModelAccounts` and `dryRun` are read from the body but not acted on** — T-908.
- **`Should_Answer401_When_NoApiKeyIsSent` was the one test green during the RED**, because an unknown route without a
  key is also a 401. It only became meaningful once the route existed; it is kept as a regression guard.
- **The caller's `payee` is honoured on a numbered check**, where FR-6 leaves the payee blank for a statement line.
  This is a deliberate divergence between the two entrances — dropping a name the caller explicitly sent would
  silently discard their instruction — and is raised as **Q-58**.
- **String-length hardening (FR-A-17)** and the 2 MB body cap are still T-911.
- **No coverage number** — unchanged from T-901…T-906.
