## 4. What is NOT verified here

**The COM probe itself has no automated test and is not known to work.** `QbSdkProbe` calls `Type.GetTypeFromProgID`,
`OpenConnection2` and `CloseConnection` through late binding; none of that is exercised by `dotnet test`, because
CLAUDE.md rule 1 forbids a test from reaching a real SDK. What the suite proves is the contract around it: the
response shape, the status codes, the fallback where the SDK cannot exist, and that the endpoint asks the probe rather
than the gateway.

Specifically unproven until the server checklist in `docs/tracker.md` is run:

- that `OpenConnection2` without `BeginSession` really does avoid the certificate dialog;
- that `Process.GetProcessesByName("QBW")` finds QuickBooks in the operator's Windows session, and that
  `MainModule.FileName` is readable with the rights the app has (the code already falls back to reporting the name
  without a bitness);
- that a second call in the same process succeeds — COM apartment behaviour across repeated STA threads.

## 5. Known gaps and decisions

- **Supported qbXML versions are not enumerated.** FR-A-3 asks for them, but the SDK exposes the list through
  `QBXMLVersionsForSession(ticket)` and a ticket requires `BeginSession` — which the same requirement forbids. Rather
  than guess, the probe reports only the configured version and claims nothing about acceptance. Raised as **Q-55**.
- **No `serverPath` / `serverBitness` for the request processor.** FR-A-3's example includes them; reading them means
  the registry, and `Microsoft.Win32.Registry` is a package `CLAUDE.md` does not allow. The bitness question is
  answered instead from the running `QBW.exe`, which is the comparison that actually matters.
- **No coverage number** — unchanged from T-901/T-902.
- `FakeQbGateway.CompanyFileCalls` was added so test 5 asserts the absence of a company-file call rather than
  inferring it from an empty request list.
