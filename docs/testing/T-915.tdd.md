# T-915 — TDD evidence

**The silent no-op: `allowModelAccounts` and the `qb:post:ai` scope.** Branch `m9-api-v1`, 2026-09-23.

Not a planned M9 task. It was found while writing `docs/M9-COMPLETE.md` §2.4, and the owner authorised the fix after
the milestone was closed.

---

## 1. The defect

`DirectRequest.AllowModelAccounts` shipped through the whole of M9 with these properties:

| | |
|---|---|
| Declared | `src/QbAutopost.Core/Api/DirectRequest.cs:50` |
| Documented | `wwwroot/openapi.json`: *"Let the model choose an account for a row no rule resolves. Needs the `qb:post:ai` scope as well."* |
| Specified | `docs/spec-api-v1.md:359`: *"`true` permits tier 3–4 (Hermes) account choice for rows without `lineAccount`"* |
| Given a scope | `ApiScopes.QbPostAi` = `qb:post:ai`, listed in `ApiScopes.All` and in the spec's scope table |
| **Read by production code** | **Nowhere.** `grep -rn "AllowModelAccounts" src` returns the declaration and nothing else. |
| **`qb:post:ai` checked** | **Nowhere.** `grep -rn "QbPostAi" src` returns the constant and the `All` list. |

So a caller could set the flag, be granted a scope minted specifically for it, and receive a batch in which every row
no rule resolved was held as `unknown-account` — with nothing in the response, the log or the audit file saying the
model had never been asked. The API promised a capability it did not have, and failed in the one direction that costs
an integrator a day: silently, and looking like a data problem at their end.

T-910's evidence noted in passing that `qb:post:ai` "has no effect yet". No tracker row ever said the feature was
unimplemented, and the OpenAPI document — the thing a caller actually reads — described it as working.

## 3. The decision, and the two it was chosen over

Refuse the batch with `400` when `allowModelAccounts` is true, from **`DirectRequestReader`**.

- **Why refuse rather than accept-with-a-note.** A note is only read by a caller who is already suspicious. The flag
  means "choose accounts for me"; the server cannot, so answering 200 answers a question that was not asked. Refusing
  costs the caller one field and tells them immediately. It also posts strictly less, which is the tie-break
  `CLAUDE.md` rule 4 asks for.
- **Why not implement it.** `docs/spec-api-v1.md` says the flag *should* work, and "spec wins over code" — but Q-51
  has never been answered, and implementing it unattended would put a model in charge of which account money lands
  in. That is precisely what rules 3 and 4 exist to prevent. The contradiction is recorded, not resolved.
- **Why in the reader, not the endpoints.** `DirectRequestReader.Read` already feeds both `/quickbooks/transactions`
  and `.../validate`, and both already render `DirectReadResult.Errors` as a 400. One change makes them agree. A
  validate that accepted what the post refused would be worse than either failure alone — it is the exact shape of
  bug that makes a caller trust a dry run they should not.
- **Why the scope is not now enforced.** `qb:post:ai` guards a feature that does not exist; a check on it would be
  theatre, written against guessed semantics. The flag is refused for everyone, holder or not. The scope stays
  reserved, and the OpenAPI document now says it is checked nowhere.

## 5. Known gaps — what this does **not** prove

1. **The feature is still not implemented.** This task made the API honest; it did not make the model choose
   accounts. Q-51 is still open and still the owner's to answer.
2. **`docs/spec-api-v1.md:359` is now knowingly out of step with the code.** The spec says `true` permits tiers 3–4;
   the code refuses it. That was left deliberately — "spec wins over code" means an agent must not quietly rewrite
   the contract to match what it built. The owner resolves it, in either direction.
3. **`qb:post:ai` remains decorative.** It is in `ApiScopes.All`, so `new-api-client.ps1` will happily grant it, and
   granting it confers nothing. Nothing warns an operator who grants it.
4. **No caller has ever sent this flag in anger.** As with all of T-907…T-914, the behaviour is proven against
   `FakeQbGateway` and `FakeHermesClient` only; nothing here has met a real QuickBooks.
5. **The refusal is whole-batch.** A caller sending 500 good rows plus the flag gets none of them posted. That is
   intended — they asked for account selection they will not get, so the rows that would have been held are exactly
   the ones they cared about — but it is a harder failure than holding the unresolved rows would have been.
6. **Nothing detects the next no-op of this kind.** There is no test asserting that every field on `DirectRequest`
   and every scope in `ApiScopes.All` is read somewhere in production. This defect survived eight tasks and a
   hand-authored OpenAPI document with a drift test; that drift test compares routes, not semantics.
