## 1. User journeys

1. As an API caller, I want every route under `/api/v1/…` so I can pin my integration to a version.
2. As the POC package and `start-all.ps1`, I want the flat paths of spec §6 to keep working, so the shipped
   scripts do not break the day the API is versioned.
3. As the owner, I want a log warning when a flat path is used — but not one per request — so I can see which
   callers must move before Q-53 turns the legacy routes off.
4. As the owner, I want `Api:LegacyRoutes=false` to make the flat paths disappear, so the surface can be locked down.
5. As a monitor, I want health to need no API key under either prefix (spec §6).
6. As the operator on the server, I want the exe to read its own `appsettings.json` regardless of which folder it was
   started from (session-13 defect 1: started from `C:\Users\…` it ran with an empty `Company:Name` and Hermes on).

## 4. Coverage and known gaps

- **No coverage number.** The solution has no coverage package (`coverlet` is not referenced) and `CLAUDE.md`
  forbids adding NuGet packages without a tracker question, so the 80 % figure in the TDD skill could not be
  measured. Reported instead: 25 new tests, and every branch of the three new units
  (`ApiRoutes.IsHealth`, `ContentRoot.Select`, `LegacyRouteLog.ShouldWarn`) has at least one test.
- **Not covered by an automated test:** that a *published* exe started from another working directory now finds its
  `appsettings.json`. The decision logic is unit-tested; the end-to-end behaviour needs the server and belongs on the
  M9 server checklist. Until then the claim is "the rule is right", not "the exe was observed".
- **Deliberate:** the legacy warning does not name the caller. Per-caller identity arrives with `clients.json` at
  T-910; the message carries the route only.
- **Untested by design:** nothing here talks to a real QuickBooks or Hermes (`CLAUDE.md` rule 1). All host tests run
  against `FakeQbGateway` / `FakeHermesClient`.
