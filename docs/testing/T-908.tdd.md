## 1. User journeys

1. As a calling system, I want to post transactions as JSON and get back the QuickBooks TxnIDs, without ever
   assembling a job folder.
2. As the owner, I want to know — after a crash, a power cut, anything — **who asked us to post that**. The request
   must be on disk before a single byte reaches QuickBooks.
3. As the owner, I want a direct post to be undoable exactly like a folder posting, with one mechanism, not two.
4. As a caller, I do not want my HTTP connection held open for an unbounded time; if it is slow, give me a batch to
   poll.
5. As the owner, I want a dry run to be genuinely dry.

## 5. Decisions

- **The ledger stays the one record of what posted.** `ApiBatchStore` holds evidence (request, state, qbXML); the
  `LedgerJob`/`LedgerEntry` rows are written exactly as a folder job writes them. That is what makes test 25 pass
  with **no change to `BatchUndo` or the undo endpoint**, and what keeps G4 catching a repeat across both entrances.
  The handoff's warning — "do not invent a parallel store" — is the reason this is split that way.
- **A refused request gets no batch id and no folder.** Identity is only granted to a request the app has accepted;
  otherwise every malformed call would leave an undoable-looking artefact behind.
- **`Unavailable` is an explicit field, not a parsed message.** The endpoint answers §2's 503 for "QuickBooks was
  unreachable" and "the backup guard refused" by reading a boolean, never by matching on `Error` text. The body is
  still the batch, so the caller learns its id.
- **The 202 path never cancels the work.** `JobQueue.RunExclusiveAsync` already runs work to the end when the caller
  stops waiting, so the timeout bounds only the wait. `Prefer: respond-async` is the same code path with a zero
  budget, rather than a second mechanism.
- **A dry run is persisted as a finished batch in `ready`.** It costs nothing and makes a dry run auditable.
- **Status follows the folder path**, not a new vocabulary: `posted` when nothing is held, `partial` when something
  is, `failed` only when the app refused to send at all.

## 6. Known gaps — what this does **not** prove

- **No real QuickBooks has seen any of this.** Every test runs against `FakeQbGateway`/`SimulatedQuickBooks`. The
  qbXML is the same the folder path sends (pinned by T-906's byte-identical test and FR-9's golden files), but the
  **server checklist for a direct post has not been written or run** — it belongs with T-802/T-803.
- **`POST /api/v1/batches/{id}/post`** — FR-A-8 says a dry run's `ready` batch can be posted later. That route does
  not exist; the route table does not list it either. A caller must re-send the batch with `dryRun:false`. Raised as
  **Q-59**.
- **`allowModelAccounts` is still not honoured** (Q-51): tiers 3–4 never run on the direct path, in the post as in
  the validate. A row no rule resolves is held.
- **Idempotency is T-909.** Without an `Idempotency-Key`, a caller who retries after a timeout relies on G4 to hold
  the repeat — which it does, but the result is a `partial` batch rather than a replayed answer.
- **Evidence is never aged out** (Q-52): `Paths:ApiBatches` grows without limit. `ApiBatchStore.All()` reads every
  batch to count attempts, which is also **O(batches) per post** — fine for hundreds, wrong for a hundred thousand.
  Both wait on the retention answer.
- **A concurrent post of the same reference could pick the same attempt number.** `NextBatchId` reads the folder
  before the work is queued, so two requests arriving together could both see `#1`. The queue serialises the
  *posting*, not the id allocation. Not reachable through today's single shared key, and T-909's idempotency store is
  where a proper claim belongs — recorded here so it is not forgotten.
- **No coverage number** — unchanged from T-901…T-907.
