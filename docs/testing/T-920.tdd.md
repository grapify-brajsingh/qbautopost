# T-920 — TDD evidence

**A missing rules file answered `500` with a stack trace.** Branch `m9-api-v1`, 2026-09-24.

Found while running the host by hand during T-919. `dotnet run` in Development, then any route that loads rules:

```
System.IO.DirectoryNotFoundException: Could not find a part of the path
  'D:\qb_post\src\QbAutopost.Api\bin\samples\rules.json'.
   at QbAutopost.Core.Mapping.Rules.Load(String path) in Rules.cs:line 67
   at QbAutopost.Api.Endpoints.QuickBooksEndpoints.ValidateTransactions(...) in QuickBooksEndpoints.cs:line 139
```

---

## 1. Two defects, one symptom

**The path was wrong.** `appsettings.Development.json` named `../../samples/rules.json` — written for the *project*
folder. But the content root is `AppContext.BaseDirectory` (T-901, and deliberately so: session-13 server defect 1
was a published exe started from `C:\Users\…` that found no `appsettings.json` at all and ran with Hermes enabled
against the wrong configuration). Two levels up from `bin\Debug\net8.0` is `bin\`, so the app looked in
`bin\samples\rules.json` and nothing was there.

**The failure was ungracious.** That is the part worth fixing properly. `Rules.Load` let whatever IO exception the
path produced escape, and it surfaced as a bare `500` — no problem details, contrary to the conventions
(*"Errors from endpoints: RFC 7807 problem details"*), and a stack trace in the operator's log instead of a sentence.

The app is **allowed** to run without the file, and that is a design decision, not an oversight: `StartupLog.cs:61`
warns *"every job will fail until it exists"* and `Readiness.cs:43` reports `rules: false` on `/health/ready`. The
system already knew and already said so. It just threw when asked to do work.

This cost real time twice in one session — the second time it silently misled me: a probe of the unknown-name check
edited `src/QbAutopost.Api/data/qb-lists.json` while the host was reading
`bin/Debug/net8.0/data/qb-lists.json`, so the test appeared to prove the check does not fire. It does. The same
content-root resolution was behind both.

not**, which is exactly how a route could answer `500` in a suite of 510 green tests.

## 3. The decisions

**`503`, not `500` or `422`.** The server is running and the caller's request was fine; the *server* cannot do this
work. That is what `503` means, and it is the same answer `/health/ready` implies. `500` says "a fault" and invites a
retry that cannot succeed.

**Checked in `Rules.Load`, not in the endpoint.** Five call sites read that file — two endpoints, `DirectPostRunner`,
`JobPipeline`, `QbListSync`. Handling it where it was noticed would have fixed one route and left four throwing;
`Should_Answer503_When_TheRulesFileIsMissingOnTheFolderPath` is there to pin that, and it covers the folder entrance
which nobody had reported.

**Typed, not a catch on `IOException`.** A missing parent folder raises `DirectoryNotFoundException` and a missing
file `FileNotFoundException`, and neither could be told from a genuine IO fault — catching the base class would have
turned a failing disk into "check your configuration". `RulesFileNotFoundException` is raised from an explicit
`File.Exists` check, and the handler returns `false` for anything else so a real fault still looks like one.

**The message names the resolved path.** The entire defect was a path resolving somewhere nobody expected, and every
message about it said only that something was missing. The detail now reads: *"Company:RulesFile resolved to '…' and
nothing is there. Relative paths are resolved against the content root — the folder the executable is in — not the
working directory."* `Should_NameTheResolvedPath_When_TheRulesFileIsMissing` asserts the path is in the body, because
a message that omits it is the message that already failed to help.

**The Development path is fixed by moving the file, not by counting `../`.** The correct relative depth from the
output folder differs between Debug (`bin/Debug/net8.0`), Release and publish, so a literal `../../../../../` would
be right in exactly one configuration and quietly wrong in the others. Instead the csproj copies
`samples/rules.json` beside the executable, `Condition="'$(Configuration)' == 'Debug'"` and
`CopyToPublishDirectory="Never"`, and the setting is a plain `samples/rules.json`. **A published server can never be
handed sample rules** — that is what the two attributes are for, and it matters because those rules name fictional
accounts that would map real money.

## 4. Verification

- `dotnet build -warnaserror` — 0 warnings, 0 errors.
- `dotnet test` — **Core 866 (unchanged), Api 513 (was 510)**, twice consecutively.
- **Against the running host, which is where this was found.** `ASPNETCORE_ENVIRONMENT=Development dotnet run` with
  **no environment override**: `POST /api/v1/quickbooks/transactions/validate` answered **`HTTP 200`** where it had
  answered `500`, and `/health/ready` reported
  `{"name":"rules","ok":true,...,"message":"…\\bin\\Debug\\net8.0\\samples\\rules.json"}` — the resolved path, which
  is the fact that was missing.

## 5. Known gaps — what this does **not** prove

- **Only the *missing* file is handled.** A rules file that exists but is **corrupt or empty** still throws
  `InvalidDataException`/`JsonException` into a bare `500`. That is the same class of defect and it is not fixed
  here: widening the handler to those would mean catching exceptions that can also come from a caller's own JSON,
  and guessing which is which is precisely what rule 4 says not to do. **Recorded, not fixed.**
- **`Paths:QbLists` was not changed.** It has the same content-root resolution, but a missing lists file is already
  handled (`QbListsStore.Load` returns `QbLists.Empty` when `File.Exists` is false), so it does not throw — it
  silently disables the unknown-name check instead. Whether *that* silence is right is a separate question and is
  not this task's to answer.
- **The `Debug`-only copy is not asserted by any test.** `dotnet test` runs in Debug, so a Release or publish build
  dropping the file would not be caught by the suite — only by a publish, by hand.
- **No live QuickBooks.** Every assertion runs against `FakeQbGateway` (rule 1).
