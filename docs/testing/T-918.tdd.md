**Q-66 answered: the API reference needs no key in Development.** Branch `m9-api-v1`, 2026-09-23.

An owner decision applied, not an agent's judgement call. T-913 chose the stricter of two readings and wrote down
what it cost; running the app made that cost concrete; the owner chose the spec's literal rule instead.

---

## 1. How this came about, including the part I got wrong

Running the host (session 23) showed `GET /api/v1/reference` answering **401 to a browser**, and I reported it as a
new defect. It was not. `ApiRoutes.ScopeFor` carried a deliberate, reasoned comment — *"api-v1 asks for `health:read`
'in Production'; this asks for it everywhere … the stricter reading, as rule 4 requires when the spec allows two"* —
and **Q-66 already recorded the exact consequence**, verbatim: *"the key travels in a header, so the page cannot be
opened in a plain browser at all … Relaxing it for Development is a one-line change in `ScopeFor` plus an
`IHostEnvironment`."*

So there was nothing to file. What the run added was not a discovery but a **confirmation**: the predicted cost is
real and total. A documentation UI that no browser can open is not a locked-down feature, it is an absent one.

The owner then answered Q-66. That is what this task implements.

## 2. What FR-A-18 actually says

> Both are served only when `Api:Reference:Enabled=true` (default **true** in Development, **false** in Production)
> and, **in Production**, require the `health:read` scope.

The spec states the Production rule and is silent on Development. T-913 read the silence strictly; the owner reads it
literally. Either is defensible — which is precisely why it was a question rather than a bug.

## 4. The change, and what was deliberately not changed

`ScopeFor(string method, PathString path, bool isDevelopment = false)` returns `null` for the documentation routes
when Development, `health:read` otherwise. `ApiKeyMiddleware` passes `environment.IsDevelopment()`.

- **The default is `false`.** Every existing caller — including both `OpenApiDriftTests` call sites — keeps the
  strict answer, so the document is still checked against the **Production** contract it declares. A future caller
  who forgets the parameter gets the closed answer, which is the failure everybody survives.
- **Only the documentation moves.** Asserted directly: with `isDevelopment: true`, `POST /quickbooks/transactions`
  still needs `qb:post` and `GET /jobs` still needs `jobs:read`. Development opens the docs and nothing else.
- **Startup says so out loud.** With `Api:Reference:Enabled` and Development, the host logs a Warning naming the
  route and telling the operator to set `ASPNETCORE_ENVIRONMENT=Production` on a real server. An operator who has the
  environment wrong on a real machine learns it from their own log rather than from someone else's browser.
- **`Api:Reference:Enabled` still ships `false`**, and `TransportGuard` still refuses a non-loopback bind without
  TLS. Two independent things must both be wrong before this is reachable off the machine.

## 6. Known gaps — what this does **not** prove

1. **No browser has rendered the page.** The HTML shell and both scripts serve with the right sizes and status
   codes; whether Scalar then paints a usable document was not observed. A 4 MB bundle arriving is strong evidence,
   not proof.
2. **`ASPNETCORE_ENVIRONMENT=Development` on a real server now exposes the documentation** to anyone who can reach
   the port. That is the whole content of the decision, and it is guarded by a startup warning rather than by
   refusal. If the owner would rather it refuse — say, refuse to serve the reference unauthenticated on a
   non-loopback bind — that is a further change, not this one.
3. **The document still declares `health:read` for these routes** in `openapi.json`, which is the Production truth
   and is now slightly untrue in Development. The drift test asserts the Production rule deliberately. A reader in
   Development is not misled in a harmful direction — the document claims *more* security than applies, not less —
   but it is a known inexactness.
4. **Q-67 is untouched.** `Authorization: Bearer` is still not accepted, by the same reasoning T-913 recorded:
   accepting a second authentication header is a change to the security surface, and belongs with the auth task
   rather than being smuggled in beside a documentation fix.
5. **Nothing here has met a real QuickBooks**, as with everything from T-907 onward.
