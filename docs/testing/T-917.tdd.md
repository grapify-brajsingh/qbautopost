# T-917 — TDD evidence

**Extending T-916's guard found a second decorative field, and implemented it.** Branch `m9-api-v1`, 2026-09-23.

T-916 guarded `DirectRequest`/`DirectRow` and the scope list, and its own gaps section admitted the obvious hole:
*"Only two types are covered. `CompanyFileRequest`, `ConnectionTestRequest`, `CreateJobRequest` and the settings
classes are not."* Closing that hole immediately turned up `requireBackup`.

---

## 1. What the guard found

`CompanyFileRequest.RequireBackup` — the same shape of defect as T-915's `allowModelAccounts`, one file away:

| | |
|---|---|
| Declared | `QuickBooksEndpoints.cs:19` — `sealed record CompanyFileRequest(string? CompanyFile, bool? RequireBackup)` |
| In the spec's own example request | `docs/spec-api-v1.md:246` — `{ "companyFile": null, "requireBackup": true }` |
| Documented | `openapi.json:772` — `"requireBackup": { "type": "boolean", "nullable": true }` |
| **Read by production code** | **Nowhere.** 0 references. |

`backupFreshness` was hard-coded to `Warning` in all three of its branches, so a caller who asked for a backup
guarantee got `ok: true` and a warning they had to notice for themselves.

Two decorative fields, found by the same guard, in two consecutive tasks. That is the argument for the guard.

**(b) The behaviour.** Three tests written against a validator that had no such parameter:

```

CompanyFileValidatorTests.cs(189,58): error CS1739: ...
CompanyFileValidatorTests.cs(206,58): error CS1739: ...
```

**A flaw in my first draft of the guard, recorded because it matters.** It excluded the *declaring* file from the
scan, copying T-916 — which is right for a Core DTO consumed elsewhere, and wrong here, because an endpoint's nested
record is consumed by the very file that declares it. All three cases failed, including two that were fine. The scan
now excludes nothing: a positional record writes `bool? RequireBackup` with no leading dot, while every read is
`request?.RequireBackup`, so the declaration cannot match itself.

## 3. The decision

`requireBackup: true` raises `backupFreshness` from `Warning` to `Error`, so a stale backup makes `ok:false` → 422.

- **Why implement rather than refuse**, where T-915 refused `allowModelAccounts`: that flag asked the system to post
  **more** (a model choosing accounts) and needed an unanswered policy question. This one asks it to refuse **more**.
  Rule 4 points the opposite way for the opposite request. And `requireBackup: true` is in the spec's own example —
  refusing the documented request would be perverse.
- **Why an unset `QuickBooks:BackupFolder` now fails too** when the flag is set. "I cannot check" is not "yes" to
  somebody who asked for a guarantee, and an unconfigured backup folder is the likeliest state on a fresh install —
  precisely when somebody sends `requireBackup: true` to find out whether they are safe.
- **Why the default is untouched.** Without the flag every branch stays `Warning` and `ok` stays true, so FR-A-5
  behaves exactly as it did. The old `ValidateAsync(companyFile, ct)` overload remains and delegates with
  `requireBackup: false`, so the eleven existing call sites did not change.
- **Why this is a SPEC-GAP.** The spec shows the field and never says what it does. This is the conservative reading,
  not a stated one. Marked `// SPEC-GAP T-917` and recorded as **Q-72**.

## 5. Known gaps — what this does **not** prove

1. **The semantics are invented, not specified.** The spec shows `requireBackup` and never defines it. If the owner
   meant something else — "check the backup at all", say — this is wrong, though wrong in the direction of refusing
   more. Q-72 exists to settle it.
2. **Nobody has ever sent this flag.** Like everything from T-907 onward, it is proven against `StubGateway` and
   `FakeQbGateway`. No real QuickBooks, no real backup folder, no real `.QBB`.
3. **The guard still cannot see semantics.** It proves `RequireBackup` is now *referenced*. It cannot prove the
   reference does the right thing — a field read into a variable and ignored would satisfy it.
4. **Settings classes are still unguarded.** `AppSettings` and its nested classes are exactly the kind of surface
   where a dead knob hides, and nothing checks them. They were not audited by this task.
5. **The token scan's weakness is unchanged from T-916.** `CompanyFile`, `Folder`, `DryRun` and `Force` are common
   enough tokens that they would pass unread. Only distinctive names — `RequireBackup`, `AllowModelAccounts`,
   `IncludeCompanyInfo` — are genuinely protected.
6. **Two found, unknown remaining.** Two decorative fields in two tasks is not evidence that there are no more; it is
   evidence that nobody was looking. The settings classes and the response DTOs have never been swept.
