# T-919 — TDD evidence

**A batch that posted nothing reported `partial`.** Branch `m9-api-v1`, 2026-09-24.

Found by the owner running a real post, not by a test. 134 rows of a December 2019 bank statement went to
`POST /api/v1/quickbooks/transactions`; every one was held `date-too-old` against the shipped
`QuickBooks:AllowedDateWindow:MaxAgeDays` of 730. Nothing reached QuickBooks — the request answered `200` in 35 ms
with `"status": "partial"`, `"posted": 0`, `"held": 134`.

---

## 1. The defect

`docs/spec-api-v1.md` §6.1 defines the enum:

> `status` uses the existing enum: `posted` (nothing held) · `partial` (some held, or the batch was cut short) ·
> `failed` (nothing posted) · `ready` (dry run).

Nothing posted, so the answer owed was `failed`. `DirectPostRunner` had **four** exits that could return `partial`
beside an empty `posted` list, and **not one** that could return `failed` except the backup guard:

| Line | Branch | Old status | Rows posted |
|---|---|---|---|
| 90 | backup too old | `Failed` | 0 |
| 113 | G4 duplicate check threw | `Partial` | 0 |
| 127 | nothing left to post | `held == 0 ? Posted : Partial` | 0 |
| 150 | QuickBooks unavailable | `Partial` | 0 |
| 183 | after the SDK call | `held == 0 && error is null ? Posted : Partial` | 0 or more |

So `JobStatus.Failed` was unreachable on three of the four paths where nothing had been posted. The operational cost
is the point: a caller that treats `partial` as "mostly fine, review the holds" — the reasonable reading — silently
skips a batch where **none** of the money landed.

The third, `Should_ReportPosted_When_EveryRowWasAlreadyInQuickBooks`, **passed when written**. That is deliberate and
it is not evidence of anything on its own — it is a regression guard pinning the carve-out in §3, so a later
simplification to "nothing posted means failed" cannot pass unnoticed.

## 3. The decision

Status is now derived **once**, in `Finish`, from the counts it has already computed, and the five branch-level
`Status =` assignments are removed. Four exits that each decided for themselves could disagree; one derivation
cannot. The rule:

```csharp
private static JobStatus Outcome(DirectPostResult result) =>
    result.Held.Count == 0 && result.Error is null ? JobStatus.Posted
    : result.Posted.Count == 0 ? JobStatus.Failed
    : JobStatus.Partial;
```

**A skipped row does not make a batch fail**, and that is the one place this departs from the spec's literal words.
Read strictly, "`failed` (nothing posted)" would make an all-duplicate re-send a failure — but G4 skips what
QuickBooks already holds, so such a batch posted nothing *because nothing needed posting*. That is the gate working.
Calling it `failed` would train an operator to ignore the word. Only a **held** row — one refused — or an `error`
turns an empty batch into `failed`. The spec is not contradicted so much as read at the level it was aimed:
`posted`/`held` are about rows the caller asked to post, and `skipped` rows were already there.

**One existing assertion was changed, and it is worth naming.** `Should_WriteTheRequestBeforeAnythingIsSent_When_QuickBooksFails`
asserted `"partial"` — it had encoded the defect. Its subject is ordering (the request file exists before anything is
sent) and the empty ledger; both assertions are untouched. Only the status line moved to `"failed"`, with a comment
saying why. Changing a test to match a code change is what rule 2 of the unattended rules forbids; changing one to
match **the spec the code was violating** is the opposite, and the new dedicated test covers the same case explicitly
rather than incidentally.

## 4. Verification

- `dotnet build -warnaserror` — 0 warnings, 0 errors.
- `dotnet test` — **Core 866 (unchanged), Api 510 (was 507)**, twice consecutively, then a third time after the
  configuration change in §5.
- No production behaviour changed beyond the reported label: no amount, no gate, no qbXML, no ledger write. The
  backup-guard path already answered `Failed` and still does.

## 5. The configuration change beside it

`QuickBooks:AllowedDateWindow:MaxAgeDays` in `src/QbAutopost.Api/appsettings.json` raised **730 → 3000** on the
owner's decision, so the December 2019 statement falls inside the window (~2,490 days back). The **C# default in
`DirectLimits` stays 730** — only the shipped file overrides it, the same split `Api:Reference:AllowTryIt` uses, so
the next installation that copies the class default still gets the conservative answer. The suite is unaffected: no
test read the window from `appsettings.json`.

**What this widens, honestly**: any row back to roughly 2018 now passes the date gate. The gate was the only thing
standing between a caller and a posting into a closed accounting period, and it no longer is on this server.

## 6. Known gaps — what this does **not** prove

- **The status is still only a label.** Nothing here verifies that a caller acts on it. `200 OK` is still returned
  for a batch that posted nothing, by design (§2 puts the outcome in the body) — so a client checking only the HTTP
  code learns nothing new from this fix.
- **The folder path was not touched.** `JobPipeline` derives its own status for folder jobs and was not examined; if
  it has the same shape of bug, this task did not find it.
- **No live QuickBooks was involved**, here or in the report that prompted it. Every assertion runs against
  `FakeQbGateway` (rule 1). The owner's 134-row batch never reached the SDK either — which is why it is a clean
  report of the status logic and says nothing about posting itself.
- **`unavailable: true` is unchanged** on the QuickBooks-unavailable and G4-failure paths, so those still answer
  `503`. Only the word in `status` moved.
