## 1. User journeys

1. As a calling system, I want to retry a post whose connection dropped **without posting the money twice**.
2. As a calling system, I want to know the difference between "you already sent this, here is the answer" and "you
   reused a key for something else" — one is fine, the other is my bug.
3. As a caller whose request was refused for a typo, I want to fix it and resend **with the same key**, not be locked
   out of a key I chose.
4. As the owner, I want a retry that arrives while the first is still running to be told to wait, not to queue a
   second posting behind the first.

## 5. Decisions

- **A non-2xx response releases the key.** FR-A-12 does not say what becomes of a key whose request failed. Holding
  it would mean a caller who mistyped a control total could never use that key again — and, worse, a 503 from an
  unreachable QuickBooks (where nothing posted) would permanently block the retry it exists to enable. Releasing is
  safe precisely because idempotency is the *convenience* layer: G4 and the ledger catch a real repeat either way.
  Recorded as **Q-60** so the owner can overrule it.
- **Keys are scoped by (key, route, client).** A caller numbering requests 1, 2, 3 must not have an undo collide with
  a post. `clientId` is null until T-910 and already part of the key, so adding clients later changes no behaviour.
- **Validation is not idempotent.** Replaying a validate would hide a change in the rules or the ledger, which is
  exactly what a validate exists to reveal. Only FR-A-12's four mutating routes are matched.
- **The middleware sits behind the API key check**, so an unauthenticated caller can neither claim a key nor learn
  from a 409 which keys are in use.
- **An empty header is treated as no header.** HTTP cannot distinguish them, so refusing one would be a rule no
  caller could reliably obey.
- **The replayed answer carries the original status code**, not a blanket 200 as §6.5's wording suggests. Replaying
  a 202 as 200 would tell a caller their batch had finished when it had not.

## 6. Known gaps — what this does **not** prove

- **The in-process lock is not a distributed lock.** `IdempotencyStore` serialises with a `lock`, which is correct
  for one host and one worker (ADR-0003) and would be wrong for two processes over one file. Same caveat as the
  T-908 attempt-number race, and the same answer: this app is one process.
- **The whole request body is buffered in memory to hash it.** The 2 MB cap FR-A-8 asks for is T-911; until then
  only Kestrel's default request-size limit applies.
- **`clientId` is always null** until T-910, so today two callers sharing the one API key share a key namespace.
  That is the same trust boundary the shared key already implies, but it is not the per-client scoping FR-A-13 wants.
- **Retention is enforced on write, not on a timer.** A server that never receives another keyed request keeps its
  last entries for ever. Harmless, and it disappears when Q-52's retention policy is answered.
- **No coverage number** — unchanged from T-901…T-908.
