# T-912 — TDD evidence

**FR-A-16 (audit trail) and api-v1 §2.6 / §8 (`requestId`, `clientId`).**
Session 17, branch `m9-api-v1`, 2026-09-23.

What this task had to make true:

- every request carries a 26-character sortable `requestId`, echoed as `X-Request-Id`, present in every problem
  detail and on every log line;
- every **authenticated mutating** request appends one JSON line to `Paths:Logs/audit-yyyyMMdd.jsonl`, kept for
  `Api:AuditRetentionDays` (400);
- that line never carries the API key, the request body, or any statement text.

---

## 1. User journeys

1. **An accountant asks "who posted this batch, and when?"** — they open `audit-20260923.jsonl`, find the line whose
   `batchId` matches, and read `clientId`, `utc`, `counts` and `totalAmount`. Nothing in that file tells them what the
   money was *for*; that is in the batch evidence folder, behind a scope.
2. **An integrator's call fails** — they quote the `X-Request-Id` from the response. The same string is in the
   `requestId` field of the problem detail they got, in every log line of that request, and (if the call changed
   anything) in the audit file.
3. **A read-only key tries to post** — they get `403`, and the refusal is in the audit file under their own client id.
   This is the case that decided where the middleware sits (see §5).

## 6. Test specification

**`RequestIdTests` (19)** — 26 characters, URL-safe; ordinal sort is time sort across a millisecond and across 40
days; 500 ids in one millisecond are all different while sharing the first ten characters; the §2.6 pattern accepts
8 and 64 characters and `-`/`_`, and refuses 7, 65, a space, `/`, `.` and a non-ASCII letter; an acceptable inbound
id is honoured, a malformed one is replaced rather than repaired.

**`AuditLogTests` (9)** — the file is `audit-yyyyMMdd.jsonl`; one line per entry; a new day starts a new file; every
FR-A-16 field is present under its wire name, including a `jobId` that is explicitly `null` rather than absent; the
object is on one line; a file past the retention is deleted and one inside it is kept; a foreign file in the same
folder (`qbautopost-20240101.log`) is never touched; the sweep also runs on the first line of a new day; **a
retention of zero deletes nothing**.

**`AuditTrailApiTests` (13)** — through the real host with the fakes: the header is generated, honoured, or
regenerated from a malformed one; a `401` problem detail carries the same id as the header; a post writes exactly one
line with `requestId`, `clientId`, `method`, `path`, `outcome`, `status`, `batchId`, `counts.posted` and
`totalAmount`; a `GET` and a `validate` write none; the key, the memo, the payee and the account name are all absent
from the file; a `403` for a missing scope **is** recorded, under the client that was refused; an unknown key is
**not**; two calls with one `Idempotency-Key` leave `ok` then `replayed`, both carrying the key; queueing a job
records `jobId` and `accepted`; the request log line carries both the id and the client, and a startup line carries
`[-] [-] [-]`.

## 7. Decisions worth reading

1. **The audit middleware sits in front of `ApiKeyMiddleware`, not behind it.** Handoff trap 17 predicted the
   problem: the key check answers `403` by returning early, so anything behind it never sees a refusal. The
   middleware therefore runs first and records *after* the pipeline returns, reading the caller out of
   `HttpContext.Items`, which the key check fills in before it decides anything. A `429` from the rate limiter is
   recorded for the same reason.
2. **An unknown key is not audited** (SPEC-GAP T-912, **Q-64**). FR-A-16 says *authenticated* mutating requests. The
   401 is already in the operational log, and auditing it would let a stranger with a wrong key grow the money
   evidence file at will. This is the reading that records less, so it is recorded as a question rather than assumed
   settled.
3. **`outcome` and `totalAmount` are given meanings FR-A-16 does not define** (**Q-65**): `ok` / `accepted` /
   `replayed` / `refused` / `failed`, and `totalAmount` is the batch's `totals.posted` — the money that actually
   moved, which is zero for a dry run. The alternative (submitted) would put a number in the money column for a batch
   that posted nothing.
4. **The audit file is not a Serilog sink.** api-v1 §8 says it is outside `Serilog:MinimumLevel`; making it a sink
   would have been less code and one configuration change away from silently losing every posting.
5. **A retention of zero or less keeps everything.** The opposite reading — "keep nothing" — deletes the evidence on
   a typo.
6. **Only four money fields are read back out of the response body**: `batchId`, `jobId`, `counts` and
   `totals.posted`. The rest of that body is payees, memos and account names, and none of it belongs in this file.
7. **`requestId` and `clientId` got their own columns in the log template** rather than being folded in with `jobId`,
   because `LoggingApiTests` greps `[2026-08-tropicana]` as a whole column and that assertion is worth keeping.
8. **`X-Request-Id` is set through `OnStarting`**, so a refusal written by a middleware that returns early carries it
   too — the same reason `SecurityHeadersMiddleware` does it that way.

## 8. Known gaps — what this does **not** prove

1. **Nothing here has run against a real QuickBooks.** Every posting in these tests went to `FakeQbGateway`. The
   audit line's `batchId`, `counts` and `totalAmount` come from the response body, and that body has only ever been
   produced by the fake.
2. **The 400-day retention has never elapsed.** `AuditLogTests` moves the clock by hand; no file in this repository
   has ever aged out of a real installation.
3. **Concurrency is untested.** `AuditLog.Append` takes a lock and appends, but no test writes from two threads at
   once, and no test runs two processes against one file. On the server there is one process, so this is a gap in
   the proof rather than a known defect.
4. **A disk-full or read-only `Paths:Logs` is untested.** `Record` swallows `IOException` and
   `UnauthorizedAccessException` into an error log line — deliberately, because the caller already has their answer —
   but no test forces that path.
5. **`clientId` on *every* line is proven only for the request line and the startup line.** Lines written inside the
   job worker for a direct batch inherit the `LogContext` push, which is asserted nowhere.
6. **The file has never been read by the tool that will read it.** Nobody has opened `audit-*.jsonl` in whatever the
   owner uses; the format is asserted field by field in tests, not by a reader.
7. **The `RouteValue` fallback for `batchId` is untested.** Every route that produces a batch id also puts it in the
   response body, so the `/batches/{id}/...` fallback has never been the thing that supplied the value.
8. **Q-62 is explained, not eliminated.** The retry makes the suite reliable on this machine; a slower machine could
   still exhaust ten attempts, in which case the folder is left in the temp directory and the test still passes.
