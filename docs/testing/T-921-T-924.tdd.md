## 1. The security defect, found before it shipped

`ApiRoutes.ScopeFor` matched the posting route by exact string:

```csharp
if (p == "/quickbooks/transactions") { return get ? QbRead : QbPost; }
return p.StartsWith("/quickbooks/") || p == "/qb/sync-lists" ? QbRead : Admin;
```

`/quickbooks/transactions/validate-and-post` is not `/quickbooks/transactions`. It would have fallen through to the
second line and resolved to **`qb:read`** — the scope issued for reading lists and validating offline. **A route
that posts real money would have been gated behind the read scope.** Nothing would have warned: the route works,
the drift test compares routes rather than semantics, and every other test passes.

Everywhere else in that file an unmapped route falls through to `admin`, which is closed. Under `/quickbooks/` the
fall-through *opens* instead. That asymmetry is the whole defect, and it is why the branch is now explicit and
carries its reasoning in a comment rather than in a name.

Pinned by two tests, in two different ways — the second is the one that would survive a refactor:

- `SyncPostApiTests.Should_Answer403AndPostNothing_When_TheKeyHoldsOnlyQbRead` — a real client key holding exactly
  `qb:read` posts through the real host, is refused 403, and `Gateway.Requests` is empty.
- `Routing/SyncPostRouteTests.Should_NotRequireOnlyQbRead_When_TheRouteWouldFallThroughToTheQuickBooksBranch` —
  states the trap as a fact: the path *is* under `/quickbooks/`, it *is not* `/quickbooks/transactions`, and it
  must not resolve to `qb:read`.

The route is matched by its exact path, never by shape. It ends in `post` and contains `validate`, so any
`EndsWith("/post")` or `Contains("validate")` shortcut clever enough to catch this route would misfile its
read-only `/validate` sibling — which is in `ReadOnlyPosts` and must stay there.

Two related lists were checked at the same time: the route is **not** in `ReadOnlyPosts` (so it is audited,
FR-A-16) and it **is** in `IsIdempotent` (so `Idempotency-Key` is honoured, §3, and `RateLimitPolicy` puts it in the
posting bucket rather than the cheaper default — the same predicate feeds both).

## 2. T-921 — `JobQueue.TryRunExclusiveAsync`

The lock taken only if it is free. The subtlety is that the idle check and the claim must be **one** step:

```csharp
if (Interlocked.CompareExchange(ref _outstanding, 1, 0) != 0) { return (false, default); }
```

A check followed by an enqueue would let two requests both read "idle", and both would post believing they held the
only QuickBooks session — the collision ADR-0006 exists to prevent.

`_outstanding` is queued **plus running**, which `Depth` (FR-A-1) deliberately is not: a caller who must not wait
needs to know about the item the worker already owns. An ordinary job releases it in a `finally` inside
`ReadAllAsync`, after the worker's `foreach` body returns — in a `finally` so that an abandoned enumeration cannot
leave the worker looking busy for ever and answer 409 to everyone after it. Exclusive work releases it earlier, and
the next section is why.

`JobQueueTryExclusiveTests` (8): idle runs · busy refuses **without enqueuing** (`Depth == 0`, so the refused work
cannot post a minute later) · eight simultaneous callers admit exactly one · a folder job merely *waiting* is
enough to refuse · the lock frees again after success and after an exception · twenty sequential calls are never
refused.

### A real race, found on the third full run

The first version released the claim only in `ReadAllAsync`'s `finally`. That is too late. The waiting caller is
resumed by `result.TrySetResult(...)` **inside** the work — which is inside the worker's `foreach` body — so a
caller who posts twice in a row could be answered **409 by the post they had just been told had succeeded**. It
failed once in three full suite runs and passed five times in isolation, which is exactly how a product race
presents itself in the field: rare, unreproducible, and blamed on the network.

The fix is an ordering: `Wrap` releases the claim before publishing the result, and `ReadAllAsync` skips items that
have released themselves (`JobWorkItem.ReleasesItself`). Releasing early is safe because a claim made in that
instant only puts an item in the channel, and the single worker cannot reach it until it has finished the current
one. Pinned by `Should_NeverAnswerBusy_When_OneCallerRunsOneAfterAnother` — twenty in a row, because once was not
enough to see it.

Two test-only timing bugs on the way, both worth recording because a test that hangs or flakes looks exactly like a
product that does. The concurrency test first deadlocked itself — it awaited the winner while still holding the gate
that would release it (both gates are now `RunContinuationsAsynchronously`, and it waits for the seven losers). It
then failed intermittently by checking that the winner was inside the work before the worker had picked the item
up; it now waits for both halves.

## 3. T-922 — the request without a dry run

`SyncPostRequest` is api-v1 §6.1's request minus `dryRun`, and it declares `bool? DryRun` and
`bool? AllowModelAccounts` **for the sole purpose of refusing them** (§2.3, T-915). Nullable so that absent and
`false` are distinguishable: `dryRun: false` is refused too, because a caller who sends it believes the field means
something here, and the next thing they send might be `true`.

`DecorativeSurfaceTests` (T-916) now scans this record as well. A field read only by its own refusal *is* read — but
if someone ever deleted the refusal and left the fields, the route would silently accept `dryRun: true` and post
anyway. That is the T-915 defect wearing a different hat, and this test is what would notice.

## 4. T-923 — `SyncPostRunner`, and the gate

No posting logic was written. `DirectPlanner.Plan` decides every row and `DirectPostRunner` performs the post —
backup guard, G4's live half, qbXML, SDK, G5, ledger — exactly as it does for FR-A-8. **`DirectPostRunner` was not
split or modified**: `RunAsync(batchId, request, plan, ct)` already takes the plan as a parameter, so the refactor
the plan allowed for was not needed, and `DirectPostApiTests` is untouched and green.

The feature is one early return:

```csharp
if (!plan.Ok) { return new SyncPost(SyncPostOutcome.Held, [], SyncPostFindings.From(plan), null, false); }
```

`plan.Ok`, and not "every row is `WouldPost`", deliberately. `Ok` is false for a held or duplicate row and true
when a row was **skipped** by a `SkipPatterns` rule — and it is the same predicate
`POST /quickbooks/transactions/validate` answers 422 on. §5.1's mitigation is that a caller validates offline
first; if the two used different gates, a caller who got 200 from `/validate` could get 422 here, which would make
the mitigation a trap. A skipped row therefore does not refuse the batch, and the 200 body reports `skipped` rows so
that `posted < submitted` is never an unexplained number.

The proof is one assertion: `Should_PostNothingAtAll_When_OneRowOfManyWouldBeHeld` sends three rows, one
unresolvable, and asserts `Assert.Empty(Gateway.Requests)` — **not** `Writes`. Not even G4's read-only duplicate
queries go out. A version of this route that posted the other two rows would pass every other test in the file.

Ordering (rule 7): the post id is taken and `Begin` writes `request.json` and `status.json` **inside** the lock, so
a refused or busy request leaves no evidence folder at all, and a 409 means nothing happened anywhere.

## 6. `postId` is the batch id, suffix and all

§6.1's example shows `"postId": "api-zemen-2019-12"`, without the `#1`. VP-8 requires
`POST /api/v1/batches/{postId}/undo` to reverse exactly this post, and undo keys off the full batch id. An id that
read prettily and undid nothing is the worse of the two readings, so `postId` is `api-zemen-2019-12#1`. The
idempotency store now records `postId` as well as `batchId`, so a replayed answer is still traceable to its posting.

## 7. What is deliberately not done

- **ADR-0008 stays `proposed`.** The plan says to accept it once Q-A and Q-D are answered. Nobody has answered
  them, and this was an unattended run, so it is not accepted here (CLAUDE.md rule 4).
- **Q-A (all-or-nothing) is implemented as the spec states it**, because the spec states it and because it posts
  less. §5.1 is explicit and ADR-0008 records the trade; the question stays open because the cost — 133 good rows
  refused over one payee — lands on the owner, not on me.
- **Q-C**: `Idempotency-Key` stays **optional**, as §3 and api-v1 §6.5 have it. Mandating a header would break
  callers that were told it was optional.
- **Q-D**: 409 immediately, no bounded wait. A wait is a queue with a small number on it (ADR-0008, alternative 4).
- **Q-B** cannot be answered here at all: the fake gateway returns instantly, so this suite can prove nothing about
  how long a real 134-row batch takes. It needs the server.

## 8. New gap found while implementing — Q-78

§6.1 says `status` is always `posted` on a 200, and on the ordinary path it is: §5.1 has already refused the
request if any row would be held. But §5.2 keeps **G4's live half and G5**, which run *after* the SDK has been
touched. If QuickBooks rejects one row of twelve, the money for the other eleven has moved, and none of §5's five
endings describes that.

An error status would tell a caller nothing was posted when some of it was — the most expensive possible lie, and
the T-919 defect in reverse. So the answer is 200 carrying the **true** status (`partial`, or `failed` if nothing
landed) with the held rows listed, and `SyncPostResult.Status` is documented as carrying it honestly rather than
being hard-coded to `posted`. Marked `SPEC-GAP T-923` and recorded as **Q-78**.

## 9. Server verification (`[server]`)

No test touches a real QuickBooks (rule 1), so the rows are `ready-for-human`. On the server:

```bash
curl -i -X POST "http://127.0.0.1:5081/api/v1/quickbooks/transactions/validate-and-post" \
  -H "X-Api-Key: <key>" -H "Content-Type: application/json" \
  -H "Idempotency-Key: zemen-2019-12-attempt-1" \
  --data-binary @samples/validate-and-post-request.json
```

Use `samples/validate-and-post-request.json`, **not** `samples/request.json` — the latter carries `"dryRun": true`,
which this route refuses with 400 by design. The new file is the same 134 rows with that one line removed.

Worth timing: the response takes as long as the whole post, which is the measurement Q-B needs.
