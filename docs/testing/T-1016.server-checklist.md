# T-1016 server checklist: PostgreSQL for saved requests

Tick each box on the QuickBooks server, in order. Every step lists what you should see. If a step does not match, stop,
write what you saw next to it, and do not go on: nothing here is urgent enough to guess. The agent has verified the same
SQL and scripts against a throwaway PostgreSQL 16 in Docker and on Windows PowerShell 5.1 with `-WhatIf` only; nobody has
run the installer on a real server yet. Background and commands: `docs/runbook.md` section 10.

Do this on a quiet day, with a recent QuickBooks backup and a copy of `C:\qb-autopost\`. The existing validate-and-post
route keeps working throughout; only the saved-requests routes and dashboard sign-in depend on PostgreSQL.

Never write a password into this file. The superuser password lives in your password manager.

## A. Before you start

- [ ] **A1. Elevated PowerShell on the server**, repository `deploy` folder present (copy the release folder if needed).
  `([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)` prints `True`.
- [ ] **A2. The PostgreSQL 16 Windows x64 installer** is downloaded from the vendor's page, and you copied the SHA-256 shown
  there. `Get-FileHash <installer> -Algorithm SHA256` prints the same hash (case aside).
- [ ] **A3. Port 5432 is free**: `Get-NetTCPConnection -LocalPort 5432 -ErrorAction SilentlyContinue` prints nothing. If another
  PostgreSQL is there, stop and ask (use `-Port` and `-ServiceName` only after deciding).
- [ ] **A4. Dry run.** `.\deploy\install-postgres.ps1 -InstallerPath <installer> -InstallerSha256 <hash> -SuperuserPassword (Read-Host -AsSecureString 'postgres password') -BackupFolder <QuickBooks:BackupFolder> -WhatIf`
  prints a `Plan:` line and `Dry run: would (1) install ... Nothing was changed.` Exit code 0. No service, no variable, no task was created.

## B. Install

- [ ] **B1. Install.** Same command without `-WhatIf`. Log lines, in order: `Installing PostgreSQL 16 ...`,
  `Superuser password set to the one you supplied.`, `listen_addresses was '*'; setting 127.0.0.1 and restarting the service.`
  (or no such line if it was already loopback), `Creating database qbautopost owned by qbautopost_owner.`,
  `Set machine variables QBAUTOPOST__Database__ConnectionString and QBAUTOPOST_MIGRATION_CONNECTION (values not shown).`,
  `Generated QBAUTOPOST__Auth__Jwt__SigningKey (value not shown).`, the migration lines of B4, and
  `Task 'QbAutopostPostgresBackup' registered: daily at 02:00 ...`, then `Done.` Exit code 0. **No password appears on screen.**
- [ ] **B2. Service and binding.** `Get-Service postgresql-x64-16` is `Running`, StartType `Automatic`.
  `Get-NetTCPConnection -LocalPort 5432 -State Listen | Select LocalAddress` shows only `127.0.0.1`
  (never `0.0.0.0` or `::`). From another machine, `Test-NetConnection <server> -Port 5432` fails.
- [ ] **B3. Machine variables exist, in a NEW PowerShell window.**
  `[Environment]::GetEnvironmentVariable('QBAUTOPOST__Database__ConnectionString','Machine') -match 'Username=qbautopost_app'` prints `True`;
  the same for `QBAUTOPOST_MIGRATION_CONNECTION` with `Username=qbautopost_owner`; and
  `([Environment]::GetEnvironmentVariable('QBAUTOPOST__Auth__Jwt__SigningKey','Machine')).Length` prints `64` or more.
  Do not print the values.
- [ ] **B4. Migrations applied.** Log shows `Running migrations.sql.`, `Running grants.sql.`, and
  `Schema is current: 2 migration(s) applied, latest 20261027200531_AuthRefreshTokenHashAndAnonymousAudit.`
  (the count grows with later releases).
- [ ] **B5. Run `apply-migrations.ps1` a second time.** `.\deploy\apply-migrations.ps1` ends with the same
  `Schema is current` line and no error (idempotent). `NOTICE: relation "__EFMigrationsHistory" already exists, skipping` is normal.
- [ ] **B6. Refuses while the app runs.** Start the API (C1), then run `.\deploy\apply-migrations.ps1`: it prints
  `The API is running (pid ...). Stop it first ...` and exits 1. Stop the API again.

## C. Start order and health

- [ ] **C1. `.\deploy\start-all.ps1`** (or sign out and in). Log shows `PostgreSQL accepts connections on 127.0.0.1:5432.`
  **before** `Starting the API:`, then `GET ... /api/v1/health/ready -> 200.` and `Database ready and schema current.`
- [ ] **C2. Database health.** `.\scripts\qb-server-check.ps1 -Step postgres -BackupFolder <QuickBooks:BackupFolder>` (key with
  `health:read`): `OK   service postgresql-x64-16 is running.`, a JSON body whose `ok` is true with no connection string in it,
  `OK   GET /api/v1/health/database answered 200.` The dump line is checked in D2; before the first backup it warns
  `No qbautopost-*.dump` and exits 1, which is correct.
- [ ] **C3. Stopped database is a warning, not an outage.** `Stop-Service postgresql-x64-16`: `GET /api/v1/health/ready` still
  returns 200 with `database` `ok: false`; a saved-requests route answers 503 `database-unavailable` with `Retry-After`;
  `POST /api/v1/quickbooks/transactions/validate-and-post` with `dryRun` still works. `Start-Service postgresql-x64-16`.
- [ ] **C4. Bootstrap admin when the database was down.** With `Stop-Service` done, restart the API with
  `QBAUTOPOST__Auth__BootstrapAdmin__Email` and `...__Password` (12+ characters) set for the account: the log warns that the
  bootstrap admin was skipped because the database is not ready, and nobody can sign in. `Start-Service`, restart the API
  **once**: the admin is created (`POST /api/v1/auth/login` with those credentials returns a token and `mustChangePassword: true`).
  Change the password, then delete `QBAUTOPOST__Auth__BootstrapAdmin__Password`.

## D. Backup and restore

- [ ] **D1. Run the task.** `Start-ScheduledTask -TaskName QbAutopostPostgresBackup`, wait a minute, then
  `Get-ScheduledTaskInfo -TaskName QbAutopostPostgresBackup` shows `LastTaskResult : 0`. The log
  `C:\qb-autopost\logs\backup-postgres-yyyyMMdd.log` ends with `Wrote <folder>\postgres\qbautopost-yyyyMMdd.dump (N bytes).`
  The task runs as `SYSTEM`: `(Get-ScheduledTask QbAutopostPostgresBackup).Principal.UserId` prints `SYSTEM`.
- [ ] **D2. Server check sees the dump.** `.\scripts\qb-server-check.ps1 -Step postgres -BackupFolder <folder>` now also prints
  `OK   newest dump qbautopost-yyyyMMdd.dump is 0.x h old (1 kept).` and exits 0.
- [ ] **D3. Retention (optional).** Copy the dump 31 times in `<folder>\postgres` as `qbautopost-2020-01.dump` ... `qbautopost-2020-31.dump`
  (names sort before the real one), run the task again: the log lists `Removed old dump ...` and exactly 30 `qbautopost-*.dump` files remain,
  the newest real one among them. Delete any leftovers.
- [ ] **D4. A real restore into a spare database** (not the live one):
  `psql` as `postgres`: `CREATE DATABASE qbautopost_restore_test;` then
  `pg_restore -d qbautopost_restore_test <dump>` with the owner or superuser password in `PGPASSWORD` for that process only;
  `SELECT count(*) FROM saved_requests;` matches the live database; `DROP DATABASE qbautopost_restore_test;`.

## E. What the application role may not do

Connect as `qbautopost_app` (take its connection string from the machine variable inside the same PowerShell process; do not
print it) with `psql`, and expect exactly these answers:

- [ ] **E1.** `UPDATE saved_request_versions SET note = 'x';` -> `ERROR:  permission denied for table saved_request_versions`
- [ ] **E2.** `UPDATE saved_request_events SET kind = 'x';` and `UPDATE user_audit SET kind = 'x';` -> `permission denied`
- [ ] **E3.** `DELETE FROM saved_requests;`, `DELETE FROM users;`, `TRUNCATE saved_requests;`, `DROP TABLE user_audit;`,
  `CREATE TABLE t (id int);` -> `permission denied` (for `CREATE`: `permission denied for schema public`)
- [ ] **E4.** `UPDATE "__EFMigrationsHistory" SET "ProductVersion" = 'x';` -> `permission denied`; `SELECT count(*) FROM "__EFMigrationsHistory";` works.
- [ ] **E5.** `SELECT count(*) FROM saved_request_versions;` works. (`DELETE FROM user_roles WHERE false;` also works: it is
  the one DELETE the app may do, for changing a user's role.)

## F. End to end through the API

- [ ] **F1. Save.** With a key holding `requests:submit` (`.\scripts\new-api-client.ps1 -Id n8n-requests -Scopes requests:submit ...`),
  `POST /api/v1/saved-requests` with `tests/fixtures/saved-requests/n8n-good.json` and `Idempotency-Key: checklist-1` returns `201`
  and a `Location` header. The same request again returns `200` and the same id.
- [ ] **F2. Sign in and see it.** As the bootstrap admin (after changing the password), `GET /api/v1/saved-requests` lists it.
  `GET /api/v1/saved-requests/{id}/original` returns the body byte for byte.
- [ ] **F3. Post on a COPY of the company file.** Only with `Company:FilePath` pointing at a copy: `POST /api/v1/saved-requests/{id}/post`
  as a user posts it; attempts show `completed`; the batch appears in `ledger.json`; undo it in QuickBooks as in T-609.
- [ ] **F4. Restart safety.** Kill the API process during a post of a test request: after `start-all.ps1` the request is marked `unknown`
  (not posted twice), and an admin can resolve it.

## G. n8n switch-over (tracker Q-81)

- [ ] **G1. Issue the new key** with `requests:submit` (runbook section 10.6, step 1). The script prints it once.
- [ ] **G2. Change the n8n node**: URL to `/api/v1/saved-requests`, new key, `Idempotency-Key` header (the email Message-ID).
  One test email returns `201`; the same email again returns `200`.
- [ ] **G3. Withdraw the old key's `qb:post`** (and `jobs:write`) in `clients.json`, or set `"enabled": false`. A call with the old
  key to `/api/v1/quickbooks/transactions/validate-and-post` returns `403` naming the scope. The n8n workflow, now on the new key, still works.
