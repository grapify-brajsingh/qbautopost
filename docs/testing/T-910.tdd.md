## 1. User journeys

1. As the owner, I want to know **which** caller asked for a posting, not merely that someone had the key.
2. As the owner, I want a read-only integration to be unable to post, even by accident.
3. As the owner, I want to revoke one caller without changing anybody else's key.
4. As a caller, I want to roll my key over without a window in which neither key works.
5. As the owner, I want a leaked `clients.json` to be embarrassing, not catastrophic — no key should be in it.

## 5. The behaviour change, and why the existing tests moved

`docs/spec.md` §6 says a key is required "on every route except `GET /health/*`". `docs/spec-api-v1.md` §2.2 — M9's
contract — narrows that to **`/health` and `/health/ready` only**. The two disagree, and 18 tests encoded the older
rule.

The narrower rule was taken, on both the versioned and the flat surface, for a reason beyond "the newer spec says
so": `/health/quickbooks` **opens a QuickBooks session** and `/health/sdk` probes COM. Left open to unauthenticated
callers once the app is reachable remotely (D-4), either one lets a stranger make the server hammer QuickBooks. One
auth rule across both surfaces was chosen over two, because a rule that depends on which path you used is a rule
nobody remembers.

What changed, and how:

- Tests asserting "health needs no key" against `/health/hermes`, `/health/sdk`, `/health/quickbooks` were
  **re-pointed** at `/health` and `/health/ready`, which genuinely need none, or **inverted** with a comment saying
  why (`Should_RequireAKey_When_SdkHealthIsRequested`).
- Tests that merely *used* those routes now send the key.
- `Should_RefuseFlatHealth_When_LegacyRoutesAreDisabled` now sends the key, so it still proves "the route is gone"
  rather than accidentally proving "the route needs a key".
- `LoggingApiTests` expected the log phrase `invalid X-Api-Key`; the middleware now says `unknown X-Api-Key`,
  because a key that belongs to no client is not malformed.
- `TransactionValidateApiTests`'s qbXML test was **inverted**: the shared key is an all-scopes client, so it now
  *does* get the body. The withholding case moved to `ClientScopeApiTests`, where a real scoped key can be used.

This is recorded as **Q-61**: an operator polling `/health/quickbooks` without a key will start getting 401 after
this upgrade, and should be told before they are surprised.

## 6. Decisions

- **Scopes map by effect, not by URL.** Anything that sends a write to QuickBooks needs `qb:post`; a route nobody
  has mapped falls through to `admin`, so a new endpoint is closed until someone decides otherwise.
- **The client list is re-read per request** (scoped resolver over a singleton store), so revoking a key takes
  effect on the next call rather than on the next restart. The cost is one small file read per request.
- **A request with no remote address fails a CIDR check.** It cannot be shown to be inside the list, so it is
  outside it. A CIDR that does not parse is skipped rather than treated as "everything" — a typo must not silently
  widen an allow-list.
- **The legacy shared key is `admin`.** It has always been able to do everything; pretending otherwise would break
  the POC package. The startup log warns whenever it is accepted alongside real clients, because while it is on it
  outranks every scope decision in `clients.json`.
- **Startup refuses when nobody could authenticate.** An empty allow-list that answers 401 for ever is a worse
  failure than one that says so once, loudly, at boot.
- **The script's hash is pinned by a test vector.** `new-api-client.ps1` reimplements the hash in PowerShell; if the
  two ever diverge, every key it issues would be silently rejected. A recorded (key, salt, hash) triple from one run
  of the script is asserted against `ApiClientStore.Matches`, so that divergence fails the build instead of locking
  an operator out at 2am.

## 7. Known gaps — what this does **not** prove

- **No TLS yet (T-911).** Keys travel in a header; over plain HTTP to a remote caller that is a key on the wire.
  Until FR-A-14 lands, the remote-caller story is *not* complete, and `Api:AllowInsecureRemote` does not exist.
- **Rate limiting and the brute-force brake are T-911.** Nothing here slows an attacker guessing keys; the 32-byte
  random key is the only defence. It is a good one, but it is the only one.
- **No audit trail yet (T-912).** The client id is resolved and logged, but FR-A-16's `audit-*.jsonl` is not written,
  so "who posted this batch" is still only in the application log.
- **`Authorization: Bearer` is not accepted**, though §2.2 calls it preferred; only `X-Api-Key` works. Deliberate —
  it is one line, but it needs its own tests and belongs with the transport work.
- **The CIDR check trusts `RemoteIpAddress`.** Behind a reverse proxy that is the proxy, not the caller;
  `X-Forwarded-For` handling is a T-911 decision (and a dangerous one to get wrong), so it is not guessed at here.
- **Scope checks are enforced at the route, not inside endpoints.** `qb:post:ai` therefore has no effect yet —
  `allowModelAccounts` is still unimplemented (Q-51).
- **No coverage number** — unchanged from T-901…T-909.
