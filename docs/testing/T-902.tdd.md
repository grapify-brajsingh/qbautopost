## 1. User journeys

1. As a monitor, I want `GET /api/v1/health` to answer in milliseconds even while a job is posting, so "the app is
   busy" is never mistaken for "the app is dead".
2. As a monitor, I want it to need no API key, like the other health routes (spec §6).
3. As the operator, I want it to name the version, process bitness, Windows session, gateway mode and Hermes mode —
   the facts that decided the session-13 server investigation — without opening a company file.
4. As the operator, I want `GET /api/v1/health/ready` to say whether the host can accept work, and to name the check
   that failed, so a bad deployment is diagnosable from one call.
5. As the operator, I want a missing `qb-lists.json` to be a warning rather than a failure: a job whose lines are all
   resolved by rules still posts.

## 4. Coverage and known gaps

- **No coverage number** — unchanged from T-901: no coverage package is referenced and `CLAUDE.md` forbids adding one
  without a tracker question. 14 new tests; every check and every branch of `Readiness.Evaluate` has a test.
- **`ok` is always true on `/api/v1/health` while the process answers.** FR-A-1 says 503 only while shutting down;
  that path has no automated test because the test host is torn down rather than drained.
- **`windowsSession` is asserted as present, not as a value.** It is `-1` where the process table cannot be read; the
  value that matters (session 9 on the owner's server, not session 0) is a server observation.
- **`activeJobId` is only asserted null.** A health call during a running job is timing-dependent; the reporting path
  is the same `IJobStore` query the job list already uses.
